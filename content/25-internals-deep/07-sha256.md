---
title: SHA-1, SHA-256 and the hash transition
minutes: 6
---

Git was built on **SHA-1** in 2005. In 2017 researchers published **SHAttered**: two different PDF files with the same SHA-1 hash. That is a **collision**, and for a system that trusts hashes completely, it is a big deal.

## What Git did

1. **Hardened SHA-1** (Git 2.13, 2017): Git uses a version of SHA-1 that **detects** the known collision attack and refuses such objects. Current Git and GitHub are protected against SHAttered-style attacks.
2. **SHA-256 repositories** (Git 2.29, 2020): you can create a repo that uses SHA-256 for every id, 64 hex characters long.

```bash
git init --object-format=sha256 new-repo
git rev-parse --show-object-format       # sha1 or sha256
```

## Why everyone has not switched yet

- SHA-1 and SHA-256 repos **cannot easily exchange** objects. Interoperability (translating between the two) is still being finished.
- **Hosting support** is the bottleneck: as of late 2025 GitHub does not host SHA-256 repositories, while GitLab has experimental support.
- Git 3.0 is planned to make SHA-256 the default for new repositories.

```fact
A SHA-1 id is 160 bits: 40 hex characters. A SHA-256 id is 256 bits: 64 hex characters. Short ids like `a1b2c3d` work the same way in both.
```

```quiz
q: Is Git today vulnerable to the SHAttered collision?
- Yes, fully
- [x] No, it uses collision-detecting SHA-1 and rejects such objects
why: Git and GitHub adopted hardened SHA-1 in 2017.

q: How long is a SHA-256 object id in hex?
- 40
- [x] 64
why: 256 bits divided by 4 bits per hex digit is 64.
```
